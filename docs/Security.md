# v3.1 privilege extensions

The helper allowlist now includes fixed DNS/NetFx3, DHCP renew/release with a syntactically validated GUID, typed Start/Stop/Restart actions for validated Windows service names (core/security protected services excluded) and catalog Install/Upgrade IDs. The helper independently resolves/downloads/verifies machine installers into its own protected NTFS directory. No caller file path, URL, script, arbitrary package or executable is accepted. Authenticated Cancel messages bind the existing session/request/nonce/process/operation and only cancel at safe checkpoints. Active servicing/installers are not force-killed. Direct downloads never fall back automatically after verification failure.

The native defenses below require Windows testing; they are not certified by static fixtures.

# Security architecture and boundaries

## Least privilege

Normal entry is a Windows GUI executable with an asInvoker/uiAccess=false manifest. No service, scheduled task, startup persistence or automatic elevation is installed. The GUI reads system information using WMI, registry, network and native APIs. It displays its actual token context, including if the user deliberately started the whole GUI elevated.

An explicit approved administrator operation starts the same executable as a separate RunAs helper process. The internal helper accepts only the maintenance/probe operations and the catalog/GUID/service extensions listed above. Executable paths and argument arrays are constructed internally from a fixed allowlist. The pipe accepts no arbitrary shell command, script, installer/download URL, user-selected module, arbitrary package ID or privileged output destination. The read-only WorkerProbe does not run maintenance.

GUI and helper hold file/directory leases for the actual local NTFS executable and its ancestors, refuse reparse handles, refuse unexpected loose DLLs and pin the exact shipped runtime configuration against the embedded copy. Image/config files deny write/delete sharing while the helper runs. Use a clean trusted local NTFS release folder. NTFS or namespace-guard errors fail closed for elevated operations. No code extraction cache or insecure recursive executable cleanup exists.

IPC uses a random local byte pipe, FIRST_PIPE_INSTANCE, PIPE_REJECT_REMOTE_CLIENTS, a protected DACL and client data rights that exclude pipe-instance creation. Kernel pipe peer PID, process creation time, session, actual image path and helper elevation are checked against held process handles. A random session/request/nonce, protocol version, strict operation/type/size/progress checks and monotonic response sequence bind one approved operation. A PID declared in JSON is not trusted as the peer identity. Alternate-admin UAC is supported by the Administrators pipe entry; it still requires Windows acceptance testing.

An admin-owned protected ProgramData coordination directory/file serializes servicing across toolkit instances. It is data-only, persists intentionally and is never executed. An unexpected owner/link is rejected. No administrator credentials are stored. No elevated worker can be used as a general software execution endpoint.

## Trust boundary

The delivered binary is unsigned. Hashes detect accidental change, not a malicious replacement of the entire application before launch. Same-token malware can interfere with a user-owned process; a local administrator can tamper with the machine. File/pipe checks are not a sandbox against such attackers, and UAC is not publisher authentication. An organization requiring assured provenance must approve/sign/distribute the toolkit through a trusted process or use an administrator-protected location. The app does not promise acceptance by Cortex, Defender, SmartScreen, AppLocker or WDAC.

An .exe.config and CLR initialization happen before Main; external process injection/profiling or a malicious replacement before startup cannot be repaired by checks inside the same unsigned application. The config comparison and lease guard the supported GUI-to-worker launch path, not an already compromised runtime. Windows operational security acceptance remains unverified until its tests are run.

## Output and lifetime

The process engine drains raw stdout/stderr asynchronously with incremental decoders and keeps CR/LF/partial output. Standard streams have independent ordering; an exact merged OS ordering is not claimed. UI display, transcript and JSONL logs are bounded separately. Queue overflow/truncation/log failure is visible rather than terminating servicing or inventing output. A slow/disconnected UI times out pipe writes; the worker continues native servicing and keeps its own log. The worker retains its own image leases if the GUI exits unexpectedly. No runtime payload extraction needs cleanup.

Normal GUI close waits while a command is active. Cancellation prevents later packages and is advisory for active servicing/installers; it does not kill DISM/SFC or an installer. Explicitly safe read-only metadata/test processes can be killed at their deadline. A hung Windows provider is not thread-aborted; inventory slots prevent unbounded replacement calls after a deadline. Native servicing monitoring stops after eight hours with an explicit incomplete-monitoring error, not a claim that the repair stopped.

## Software

WinGet is resolved from the current account's registered Microsoft DesktopAppInstaller package, not an arbitrary PATH executable. Microsoft Authenticode and availability/source JSON are checked. The named winget source must match the documented Microsoft community endpoint/type/identifier. Exact IDs, explicit source/dependency-source and catalog-only arguments are used. No force/hash/security/AV override flags are present. WinGet/Windows handle installer elevation and package verification; scope changes are not silently substituted. WinGet registration for an alternate account can differ, so the GUI runs it as the initiating account.

Post-install verification reads structured WinGet export identity/version data before and after, and registry scope evidence when explicitly requested. Unknown/failed/ambiguous evidence remains inconclusive. Registry display-name matching alone is labeled detection rather than installation proof. Update success requires observed version change, not just a pre-existing application. Version/latest metadata is never guessed from localized tables.

Direct catalog installers use exact per-vendor origin lists for every redirect, bounded downloads and protected unique NTFS staging. A held file handle prevents writes during signature/hash validation and execution. Expected publisher names are verified with WinVerifyTrust. Missing signatures are only permitted for the explicitly designated 7-Zip profile with a matching official release SHA-256; invalid signatures are never bypassed. Fixed silent arguments and scope are compiled into profiles. Post-install registry identity/publisher/version evidence must be present, with a known-release version match when available. Unknown or unchanged-update evidence remains inconclusive. Internet zone is retained. Cleanup deletes only the known installer and its empty unique directory; active files are never force-deleted.

## Policies, privacy and diagnostics

No Execution Policy change, Unblock-File, antivirus exclusion, firewall/WinRM/TrustedHosts change, certificate import or security-policy bypass is performed. Optional remote GPUpdate imports only the system GroupPolicy module and uses validated host input with fixed command code. It executes under the current identity and reports submission separately from completed processing.

Logs use protected current-user LocalApplicationData storage, random filenames, bounded background queues and redaction of common credential/token/license patterns. No inventory snapshot, product key, saved password or private key is intentionally collected into logs. Fixed command output may contain device/account information; redaction is best effort, particularly across stream chunk boundaries. Do not paste secrets into any data field. Output/export must be reviewed before sharing. Default HTML excludes full event message bodies and native command transcripts; explicitly selected text output can include them. Session JSONL logs cap at 2 MiB and retained UI transcript at 2 Mi characters; logs are retained for manual review and are not silently deleted by later instances.

If policy prevents the EXE/CLR from entering Main, an application dialog/log cannot exist; consult Windows CodeIntegrity/AppLocker/Defender/security-product logs. If the user profile is unwritable, the GUI reports logging unavailable; it cannot guarantee a diagnostic file when every allowed location is denied. If a managed startup error happens after logging initializes, the dialog identifies the error and exact log path. The worker's log is stored under its elevated account's local profile; alternate-admin logs can require that administrator to retrieve them.

Machine installer directories in v1.0.0 inherit no user-write access: explicit Administrators/SYSTEM ACL and administrator owner under the guarded servicing root. MOTW uses native Unicode file handles and remains ZoneId=3. Failure to write MOTW blocks execution. Local Group Policy launches only a fixed interactive cmd /k gpupdate /force command without RunAs, helper, redirection or input replies. It uses the current process identity; starting the entire GUI elevated deliberately changes that identity. Vendor utility downloads never execute the downloaded file, preserve MOTW and require a trusted expected publisher. Official metadata resolution is limited to 45 seconds and installer streaming to 15 minutes; failed/cancelled partial files are removed where permitted.

## Selected-application uninstall

Removal is intentionally outside the restricted maintenance helper. The GUI never forwards uninstall text as elevated-helper command input. It confirms registered name/publisher/version and rereads exact hive/view/key before launch. SystemComponent, NoRemove, update/child records and conservative Windows/runtime/security/toolkit name rules block removal. This is not an exhaustive classification of every enterprise-protected third-party app; technician authorization and Windows permissions remain authoritative.

MSI accepts only a registered WindowsInstaller product-code command targeting that same GUID. It uses system msiexec /x with normal interactive UI, /norestart and REBOOT=ReallySuppress. It refuses ambiguous extra registered MSI arguments. EXE plans require a quoted absolute local path (or an unambiguous no-space path), no shell/script/system proxy and no known restart/logoff switches. Registered EXE arguments are never made silent. All EXE uninstallers require valid Windows Authenticode trust; machine EXEs additionally require an administrator/SYSTEM/TrustedInstaller-owned Program Files path without reparse points or broad write access. Unsupported registrations are left for Windows Installed apps/vendor management.

Machine-scope uninstallers use their own Windows runas request when needed; current-user records never receive a toolkit-forced runas verb. Vendor executable manifests may independently request elevation. A held image handle, registration recheck and per-user cross-instance uninstall lock narrow replacement/duplicate risks. Running uninstallers are not killed on Cancel; use the vendor's Cancel control. Launcher exit does not prove a child installer finished. Complete refreshed registration evidence is required to report removal, and file/data erasure is not asserted.

The toolkit never sends restart/logoff authorization. Arbitrary vendor behavior cannot be controlled universally; review its interactive prompts and use an authorized test machine. No security product, policy, trust store, Windows Installer policy or certificate validation is bypassed.
